# OpenHalcyon 初版设计

目标是让 Android CE 4.13.4（build 147219）在独立公益服完成一局，也能和其他运营者的实例自动组局。一个 Rust 进程提供平台、对局和管理接口，加入匹配池时启用对等共识。管理契约沿用 `1.0.0-draft.1`；项目版本、API 版本及路径前缀只在维护者明确要求发版时调整。

## CE 协议对实现的约束

通读资料库 `PROTOCOL.md` §0–9，并核对 `SERVER_DATA.md`、`read_side_tags.json`、机器可读 RPC 定义、选人抓包和回放。遇到早期推断与实测时序冲突，优先采用目标 Android build 的具体报文。以下验收边界适用于本地与跨服两种部署。

| 通道或资料 | 实现和验证 |
|---|---|
| HTTP 引导与 HTTPS 平台 | 200 加一行 host:port；旧客户端 POST 的 Content-Type 可为表单而正文是 JSON。游客首启 createGuestPlayer，再启 getPlayerForGuestAccount，随后 startSessionForPlayer、getPlayerInfo、exitLobby、update 和 manifests。用实际响应信封与 token 轮换验收。 |
| 状态推送与匹配 | 菜单心跳由 update 维持。notify WebSocket 和 fallback long-poll 共享状态序列及 time/tag 游标；聊天另有通道。joinLobby 后按实测状态推进，区分 bots 自动确认与真人接受/拒绝。playing 下发 host、port、matchId。 |
| GS 两条 TCP 连接 | 选人/控制与稍后的游戏数据连接归属同一局。长度为 u16 BE；客户端 hello 和首个服务端 ACK 均有明文样本。用两局向量验证 matchId 派生与块字序；参考脚本实际是分别反转每个 32 位字内的字节。先验 setup、模式、目录、5v5 名册和锁人，再单独验第二条连接及世界快照。 |
| Bot 名册与实体 | 5v5 选人 0x0459、回放玩家信息 0x03EE 可核对 Bot 占位、名字和英雄映射；0x03F3 出生使用实体类型表与皮肤标识。移动命令 0x03F4 有目标点样本；普通攻击、选技能、施法目标的完整真人输入分别做真机对照。 |
| 战斗输出与回放 | 位置 0x042E、状态和属性增量与回放按实体及时间对齐。静态 reader 长度、填充后的线上长度、ZB 类型槽分别处理。VGR 每段可重复携带完整开场且有内部事件；逐段初始化不能当成线上反复出生。文档对 0x041D 子类型 8 有两种解释，保留原值直到行为实验区分。 |

本地 `match_decoded.jsonl` 有 298 条记录，其中 275 条为英雄/皮肤目录；`vgr_decoded.jsonl` 有 43,160 条，含 9 条带内部 Bot 名标记的记录。前者可检验选人，后者可校准兵线与实体事件。完整 Android 多人局、最小加载快照、所有英雄交互和跨归属服入局仍需真机验收。

## 对等节点如何自动组局

每个互信匹配池是一组地位相同的 Raft 投票成员，运行相同程序，一节点一票。任何成员可接纳自己的玩家、计算配局、提议分配、承办房间、参加选举。Raft 自动选出当前任期的 leader 排序和复制写入；该角色没有额外匹配权、运营权限或托管优先级。各服账号与游客凭据留在归属服，每局由一台主机权威模拟，客户端直连主机。

- **建池与成员。** 服主配置 poolId、稳定节点 ID、可信身份及若干种子地址。新池按共同认可的初始成员配置一次性引导，持久化集群身份，重启或失去多数时沿用原集群。种子只用来发现成员。新成员先追日志，再通过成员变更提交为等权 voter；移除亦通过成员变更。实例间 mTLS 校验身份，成员来自互信运营者。Raft 的故障模型覆盖崩溃和分区，不提供恶意多数防护。[Raft](https://raft.github.io/) · [OpenRaft](https://docs.rs/openraft/latest/openraft/)
- **共识记录什么。** 入队、取消、组队席位、玩家接受、房间分配、就绪、终止和结果摘要进入复制状态机。只有归属服能提交本服身份的票，一个玩家同一时刻只允许一个活动票或房间；跨池由归属服 SQLite 持久化独占记录，旧池未确认释放前不能转池。容量通过带时效的对等公告分发。候选主机延迟随票据提交。位置、技能、Bot 感知及世界快照留在承办主机。申请命令带来源、requestId 和票据代次，重试返回原结果。
- **谁来提议。** 对已提交的等待队列，以最老的兼容票为锚，按队列/已提交票 ID 对成员做稳定散列排序，首选成员先计算，短暂延迟后其他成员可接手。不同锚分摊工作。先满足模式、规则内容摘要、整队、延迟上限和容量，再按等待顺序、队伍平衡和最差玩家 RTT 筛选。托管优先选延迟合理且资源有余量的节点，接近时按已承办负载占其容量的比例轮转；同分用稳定 ID 打破。试运行观测按节点的等待分位数、提案与托管量。公平意味着同资格同规则，弱机可限制容量。
- **防止抢同一玩家。** 任意节点可依据本地视图提出整组票、预期代次、主机和 matchId。状态机以日志顺序原子地检查并锁定全部票，可见性过时的提案整体失败。主机实时负载仅在选候选与本机准入时使用；所有副本应用命令时只读已提交数据。成员变化、随机数或本机时钟均不得让副本作出不同决定。

省略 `[federation.latency_ms]` 或将表留空时，归属服在入队时并行探测已配置的当前投票成员。探测通过成员 mTLS 发送小型请求，本机记为 0 毫秒，未响应成员略过。并发入队共享采样，完整采样缓存 20 秒，部分采样缓存 5 秒。空闲时没有定时 RTT 探测。非空的显式表继续作为主机白名单和运营者估计，不补充自动测量。

自动 RTT 衡量归属服到候选主机的应用往返时间，可能含连接建立开销。游戏客户端直连承办主机，移动网络到游戏主机的实际延迟可能不同。此机制不读取原生客户端的测速。归属服在首次向 Raft 提交前持久化整张票和本次延迟快照。超时重试、重启和取消请求沿用同一份数据。取消后重新入队会创建新票，仍可复用缓存期内的样本。

### 从排队到开局

1. 归属服接收 joinLobby 并持久化意图；入队获多数提交后进入联邦队列。任意节点接收写请求并转发给当选节点。冲突、取消、重复提交按同一票据代次裁决。
2. 一项提案原子锁定整组票。各归属服通过 CE 的 match_pending 收集真人确认，按队列策略填充 Bot。主机按 (matchId, allocationId) 幂等地暂留端口和席位。容量不够、有人拒绝或超时，由成员提议 Abort；已接受且仍愿等待的票保留原排队优先级。
3. 主机完成监听和名单准备后提交 HostReady；状态机只允许指定主机、同一分配代次、所有必要玩家已确认的分配进入 Ready。到期和取消都由日志中的条件转换决定，本地计时器只触发提议。主机观察到已提交 Ready 才接受该局游戏流量，各归属服观察到相同决定后发布 playing。两条 TCP 连接共用该局 matchId。按 (归属实例, 玩家 UUID) 保存全局身份；同局 CE 握手 UUID 冲突在预留前处理。平台 JWT 不进入共识日志。
4. 已激活房间由原主机运行到结束；Raft 换届不影响逐帧处理。主机保存并幂等提交结局，归属服按 (matchId, playerId) 应用一次。无多数时停办新的联邦分配；已开局继续，结算待恢复后提交。已在联邦排队的玩家不会因本地超时另起一局。已就绪主机失联先给重连窗口，首版不热迁移；只有主机确认停局或运营者已隔离旧主机并提交终止，才释放该局玩家。少数分区不可单方面恢复旧房间或释放其席位。
5. 三节点池容忍一台离线；双节点池需两台同时在线才能提交。独立节点可在本地开局，加入联邦时沿用同一套票据规则。首批按互信、地域和延迟预算组成小池，避免全球每次排队都跨洋等待多数。

管理 REST 沿用 `GET /api/admin/v1/federation/pools`，展示本节点角色、所见 leader、多数可用性、投票成员数、可选主机数和本服票数。管理权限以托管归属为界。实例间沿用 `/federation/v1`，在任一成员上提供票据 PUT/GET/DELETE、分配提议与状态查询、席位确认、主机就绪和幂等结算。写成功须已提交；结果不明时以原 requestId 查询或重试。决定玩家去向的查询使用线性一致读，面板可展示标明采样时间的本地视图。OpenRaft 的投票、日志复制和快照走独立的节点认证内部接口。日志、投票及状态机快照持久化，应用进度和副作用去重一起恢复。

节点间 REST 路径如下。除容量公告外，变更结果由同一池的已提交状态机决定。标识符由请求发起方稳定生成，重发不能创建第二次操作。

| 相对 `/federation/v1` 的路径 | 调用方与结果 |
|---|---|
| `PUT /hosts/{id}/capacity` | 主机向同伴发布自身带序号和有效期的容量观测，允许不同成员暂时看到不同值。 |
| `PUT /tickets/{id}`、`GET /tickets/{id}`、`DELETE /tickets/{id}` | 归属服入队、查询和取消。请求携带票据代次；取消与锁票按日志顺序生效。 |
| `PUT /allocations/{id}`、`GET /allocations/{id}` | 任意投票成员提议整组席位、代次与主机；锁票冲突返回 409，重复同一请求返回已提交状态。 |
| `PUT /allocations/{id}/acceptances/{ticketId}` | 归属服提交本票接受或拒绝；由状态机检查该票归属及分配代次。 |
| `PUT /allocations/{id}/readiness` | 指定主机报告监听就绪或预留失败；提前到达的就绪回执和玩家确认分别记录，最后一个必要条件满足时原子转为 Ready。 |
| `PUT /allocations/{id}/abort` | 成员提议取消尚未 Ready 的分配，携带原因和预期状态；已 Ready 则返回 409。 |
| `PUT /results/{matchId}` | 指定主机提交终局摘要；同一摘要幂等，不同摘要冲突。各归属服独立消费并持久化已应用标记。 |

## 队伍匹配与社交功能

队长通过 `joinLobby` 提交自己的队伍。归属服在一个 SQLite 写事务里读取成员名单、检查每人的独占席位，并为整支队伍加锁。队员在排队、确认和对局期间通过 `exitLobby` 或 `rejectMatch` 取消尚未开局的票据后即可调整队伍。开局后，名册锁随对局结束释放。结算仍由每名玩家独立退出。

本地配局按整队组合空位。联邦为一支队伍提交一张包含完整名单的票，收齐每名真人的确认后才向共识池提交该票的接受决定。取消、结果和通知投影覆盖该票的各个成员。分布式集成测试以 CE RPC 在一个归属服组成双人队，与另一个归属服的单人配局，随后连接第三台主机的控制与游戏通道。

主机最多为每侧分配五名真人。编排器先最小化被分到两侧的队伍数，再平衡两侧真人数。组队界面的手动分边保存在队伍状态中，自动匹配使用上述编排规则。`updateQuintPartyState` 支持队长原子更新队列和大厅状态。`changeGuildMembership` 支持显式加入或退出指定公会。客户端参数布局仍需真机验证。公会奖励需要运营者配置，领取时检查当前成员资格，入会奖励每账号只能领取一次。

好友旁观开放给当前未参与匹配的玩家。旁观者和可见好友必须属于同一归属服。好友的对局可以由归属服承办，也可以由同一互信池的另一台主机承办。归属服检查已确认的好友关系并持久化旁观席位，承办主机通过成员 mTLS 确认归属服身份并从多数派读取对局，检查好友确实是该归属服在本局的真人席位。缺少多数确认时暂停发放联邦旁观凭据。

HTTPS RPC 下发独立的只读连接凭据。旁观者直连承办主机，防火墙需允许其公布的旁观 TCP 端口。主机拒绝来自旁观连接的游戏指令。退出旁观、好友关系解除或目标隐藏在线状态时，归属服向承办主机撤销相应的联邦旁观凭据。归属服收到主机的撤销回执或确认该局已结束后，释放旁观席位。原生客户端旁观握手和不同归属服之间的好友关系仍待验证。

## Bot 的 Rust 实现

首个英雄选 Ringo。已核对的数据为血量 703、武器 74、射程 6.2、移速 3.6。目标是一条兵线上能补刀、保持距离、跟兵推塔、低血撤回并重新进线。先实现普攻、兵塔和水晶的胜负，再接经过校准的技能。回放可验证节奏和编码；弹速、攻击间隔、小兵 AI 及完整技能数值在资料中仍有缺口，用具名的项目规则和来源标记记录。

```rust
// 接口草图。view 只暴露该英雄可感知的信息，memory 跨决策保留。
fn decide(view: &BotView<'_>, memory: &mut BotMemory, tick: Tick) -> Option<PlayerCommand>;
```

| 模块 | 怎么写 |
|---|---|
| 感知 | 模拟为每队计算视野，空间网格索引敌我实体。BotView 只提供角色自身合法状态、可见单位、地图和带时间戳的最近目击点。丢失视野后只能朝最后已知位置搜索。 |
| 决策 | 先枚举可执行候选，例如撤到己方塔、攻击一只兵、随友军推进。按危险度、预计补刀收益、到达时间和当前目标切换代价评分。BotMemory 保存当前意图、目标 ID、下次评估 tick；分数接近时保持目标，紧急撤退可打断。 |
| 执行 | Bot 产生 MoveTo、Attack、Cast 等内部指令，和真人经过同一校验。模拟独占移动、攻击前摇、出手、后摇、能量、冷却及伤害。选定攻击后等待出手事件再走位；目标死亡、走出射程或不可见时重新计划。每个 Bot 只保存局部状态，无独立线程或 socket。 |
| 小兵、塔与团队 | 小兵有限状态机沿预制路点行走、索敌、交战和重新归线；塔复用射程/仇恨查询。团队每秒更新一次兵线和集合目标；英雄独立决定能否安全执行。技能配置描述目标类型和施放条件，由具体技能实现效果。 |
| 导航与预算 | 先制作一条有可行走边界、路点、兵塔和水晶的验证地图；英雄在可走图做有扩展上限的 A*，缓存路径。约 20 Hz 模拟下，英雄暂按 2–5 Hz 分批评估，紧急事件合并并设每 tick 预算。AI 预算用尽时沿用仍合法的上一指令，模拟继续执行全部规则。 |

**一次 Ringo 决策示例。** 友军兵线进入塔射程，敌方残血小兵在 6.2 范围内。Bot 用可见兵线和项目已校准的出手、弹道时间估算命中时血量；若有补刀窗口则 Attack(minion)。模拟确认出手后才允许走位。若敌方威胁逼近且己方兵线消失，撤往己方安全路点；塔前有兵且附近安全时才推进。Bot 可以错失补刀，不能看到战争迷雾后的目标，也不能自行改写生命值。

**如何验收。** 为补刀、脱离射程、塔前撤退、目标失去视野、施法被打断各做一个小场景；检查指令序列和模拟判定。用固定 seed、稳定遍历顺序、规则摘要和带 tick 的输入重放，同构建逐期比较状态摘要。无头 5v5 覆盖多组 seed，记录卡路时长、无效命令、每个英雄决策耗时和能否正常摧毁水晶；测试超时记失败，不能替代胜利。最后用真机进入 1 真人 + 9 Bot，验名册、出生、走位、伤害、结算和回菜单。

## 低配机器的运行预算

- 单个进程加载一次只读规则和地图，房间共享。Tokio 管网络，固定数量模拟 worker 分摊房间，每局绑定一个 worker；worker 数量和房间上限可配，单核部署也保留网络调度时间。房间内采用紧凑实体数组、稳定实体 ID 和可复用缓冲区。没有玩家或待处理事件的大厅不跑游戏 tick。
- 从 20 Hz 固定模拟步长开始验证，即每步 50 ms。这是项目起测值。模拟频率、AI 决策频率、位置广播频率分别配置；网络发送遵守 CE 客户端要求。房间错峰调度，工作队列有界。落后时限制单轮追赶步数并记录超时，不静默跳过战斗步骤。
- 对位置等可覆盖的更新按实体合并；出生、死亡、伤害、结算保持顺序。按视野和脏字段生成差量，消息批量写 socket。慢客户端使用有界发送队列，超过恢复窗口则断线并走已验证的重新同步流程。数据库和诊断日志写入不占用模拟循环。
- 准入同时检查 CPU、整轮 tick 完成延迟（含排队）、RSS、出口带宽、端口及在途预留。按真人席位与 Bot 席位组合实测 CPU/出口成本。没有容量的主机停止接局，其他节点可提议改配健康主机，已经开始的房间保持相同玩法精度。对局主机对最终预留拥有否决权。
- 容量基准用 release 构建，从 **1 vCPU / 1 GiB** 起，在另一台机器运行使用真实 CE 编解码、读取下行和发指令的负载客户端。分别测 10 真人、5 真人 + 5 Bot、1 真人 + 9 Bot；加入同屏团战、连续开局、慢连接和长期跑局。另测登录与排队峰值。
- 初始验收线：每档至少 30 分钟，tick 完成延迟 p99 ≤ 40 ms、持续 CPU ≤ 75%、RSS ≤ 可用内存 75%，无可靠事件丢失、无持续积压，出口低于运营者预算。报告并列写明硬件、带宽、构建、活跃房间数、真人数、Bot 数及每玩家出口；临界档再跑 2 小时。每种组合最后一个通过档位作为该机器配置的准入上界。真机另验手感、位置同步和完整结算。

## 项目边界与里程碑

`protocol` 负责 CE 线协议，`data` 加载规则、英雄和地图，`sim` 包含同步模拟、导航和 `ai`。`matchmaking` 是确定性的票据/分配状态机。`server` 负责平台、GS、管理端、节点传输、持久化和 OpenRaft 适配。采用 Tokio/axum、bytes/tokio-util、Serde、SQLite 和 tracing；Bot 首版用 Rust 枚举、数组与队列。容量实验单独构建无头客户端，能分别测模拟成本与每名真人的网络成本。

1. 打通游客菜单、选人、双连接、单英雄移动。从第一局记录 tick 延迟、RSS 与出口。
2. 一条兵线完成 Ringo 对战并结算，再用 1 真人 + 9 Bot 验证 AI 和真机表现。
3. 三个等权进程组成测试池，两台客户端登录不同服，非 leader 提议、第三节点托管；在选人前和对局中分别触发一次换届。应只组一局、结算一次，客户端能回各自菜单。
4. 检查并发冲突、部分成员失联、重启追日志、取消和就绪竞争、导出结算重放。运行低配容量矩阵，再给出可承载人数。
